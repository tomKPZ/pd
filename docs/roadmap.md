# Roadmap

v2 is complete and tested end to end in QEMU (all milestones done; see [design.md](design.md) and the
decision log in §13). This lists what's left, each with a recommendation.

Never done autonomously: anything involving real disks or USB sticks, pushing to the remote, external
NixOS configuration repos, and running a migration.

## Recommended next

| Item | Recommendation | Autonomous? |
|---|---|---|
| **Try pd on real hardware** | Do it next, following [manual-testing.md](manual-testing.md): QEMU can't show firmware quirks, real keyboards, storage controllers and NICs, or Argon2 timing. It also covers the YubiKey and stock boot items below. | No: needs real hardware. |

## Later

| Item | Finding | Autonomous? |
|---|---|---|
| **FIDO2 with a real security key** | Implemented and tested with QEMU's emulated CanoKey (design.md §4.1). Try it with a real key, in a VM (`-device usb-host,vendorid=0x1050,...`) or on the real-hardware trial. | No: needs a real key. |
| **Stock boot on real hardware** | Documented and tested in QEMU, including a hidden boot from the real Debian Live 13 image (`PD_TEST_LIVE=1`, [stock-boot.md](stock-boot.md)). Try it during the real-hardware trial, ideally also with Tails 7 (its Welcome Screen needs a GUI, so it isn't automated). | No: needs real hardware. |
| **Catch the decoy rising above the floor between hidden boots** | The frontier monitor sees only where the decoy's data is now (design.md §10.5). It could also scan the decoy's pool metadata for old btree nodes (`thin_scan`) pointing above the floor, and suggest `pd compact --hidden-offset N`. Worth it if decoys run close to the floor. | Yes. |
| **FIDO2 without a per-install file** | With the disk salt ([design.md §4.2](design.md#42-the-salt-and-the-disks-edges)), `fido2.cred` is all that keeps a FIDO2 user's USB specific to the install. The slots could move to the disk, encrypted under each side's Argon2 output; the disk would then change wherever they're stored whenever a key is enrolled. | Yes. |
| **Live-system boot from the release** | The release could carry the boot tools as a static bundle that a live system downloads and runs, instead of typing stock boot's commands; with the disk salt this works for pd installs too. Needs network access at boot. | Yes. |
| **GitHub Actions: build, check and release the prebuilts** | Everything a user runs can be prebuilt, since nothing in it is specific to an install any more: the boot image (`bootUki`, about 25 MB), the setup UKI (`setupUki`, which carries the boot image and the keymaps, so `pd usb` needs nothing else), `pd.pyz` for live systems, and a tarball of the static boot tools (`plainTree`, for the live-system boot above). Per-install files are made by `pd usb --config` and never come from a release. Proposed workflows: on every push, `nix build` the four, the unit tests, and a rebuild check (`nix build --rebuild` of `bootUki` and `setupUki`, which fails if a build isn't bit-for-bit reproducible); on a tag, the same plus a release with the files, `SHA256SUMS`, and GitHub's build-provenance attestation (`actions/attest-build-provenance`), so a download can be checked against the workflow that built it. A binary cache (e.g. Cachix) keeps the kernel and static builds from being rebuilt each time. The QEMU suite needs KVM, which GitHub's standard Linux runners now offer; on their 4 cores it would take a few hours, so run a fast subset (`test_e2e`, `test_uefi`, `test_usb`, `test_layout`) per push and the whole suite nightly or before a release. Opt-in tests that download (Arch, Debian Live) stay manual. | Partly: the workflow files can be written and tested with `act` locally; enabling them, adding a cache token, and the first release need the repo owner. |
